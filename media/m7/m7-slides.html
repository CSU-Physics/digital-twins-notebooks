By the end of this module you can

  • tell verification (does the code solve the model?) from validation (is the twin accurate enough for its use?);
  • connect prepared components into one twin prototype and verify the connection;
  • test the twin on held-out data and on one challenging condition, against a tolerance and a baseline;
  • read a test as meets, misses or insufficient evidence from the error and its interval;
  • complete a twin data sheet: intended use, data, results, where not to use it, one risk, and the action when confidence is low.

Three tracks, one method

Process twin

Module 3's calibrated Deal-Grove model, kept in sync by Module 5's Kalman filter. It predicts each run's monitor wafer and recommends the oxidation time.

tolerance: MAE ≤ 0.5 nm

Metrology twin

Module 4's hybrid virtual-metrology model, kept in sync with one sampled wafer per run. It predicts every product wafer from the furnace traces.

tolerance: MAE ≤ 0.5 nm

Toolset twin

Module 6's SimPy line with the drifting furnace of Module 5, calibrated from the fab's lot log. It forecasts the weekly mean cycle time.

tolerance: weekly MAE ≤ 1 h

Each track takes about 2 hours, ends with the same six-field data sheet, and has its own project quiz. You need one.

Verification and validation

  • Verification: does the code compute what the model says? Compare it with answers you can work out exactly.
  • Validation: how close are the twin's predictions to measurements, judged by the use you intend?
  • Verification first: a validation result means little if the code is wrong.
  • Definitions of the National Research Council (2012), used by the National Academies (2024) for digital twins.

Verification or validation?

  1. In Module 6 you checked that L = λW holds on the simulation's output.
  2. In Module 4 you scored three models on a time-ordered test set of later runs.
  3. The twin aims at the target with the recipe rule; its own prediction for that time is then exactly the target.
  4. In Module 3 you predicted the thin-oxide runs and found them thicker than the model said.
1 and 3 are verification: they check the code against an exact property of the model (Little's law, the inverse of the recipe rule). 2 and 4 are validation: they compare predictions with measured data, and 4 shows where the model does not apply.

Write the test plan before the test

Tolerance

From the intended use, set before any test runs. Changing it after seeing the result is not validation.

Held-out data

Data the twin never saw while it was built or tuned, in time order.

Baseline

The simplest method that could work. Not beating it is a valid finding.

One challenging condition

Harder than normal operation, built in on purpose and named in the notebook.

Predict first, then use the measurement

A twin that stays in sync keeps learning from its measurements. It can still be tested honestly: score each prediction before its measurement updates the twin. Every error is then out of sample.

The error, and how sure you are of it

MAE = mean |measured − predicted|    half-width = t0.975, n−1 · s / √n
  • One error per independent test unit: a run, or a week. The five wafers of a run share the run's effects, so they count as one unit, not five.
  • Process twin, example furnace: MAE 0.409 nm, half-width 0.071 nm, over 59 runs.
  • More test units narrow the interval, about as 1/√n (Module 6).

Three verdicts

"Insufficient evidence" is an honest result, not a failure: the test cannot tell, and more data would. A "meets" that the data do not support is the result to avoid.

Pause and predict

Which verdict?

A twin's tolerance is 1.0 h. On 10 test weeks its MAE is 1.4 h with a half-width of 0.6 h. On 24 other weeks it is 0.6 h ± 0.2 h.

10 weeks: 0.8 to 2.0 h contains 1.0, so insufficient evidence: the twin may or may not meet the tolerance there, and the data sheet must not claim it does. 24 weeks: 0.4 to 0.8 h lies below 1.0, so meets.

The challenging condition decides where not to use the twin

  • Process: the failing thermocouple; the filter, tuned for slow drift, lags behind.
  • Metrology: after a thermocouple replacement the traces change meaning; the interval is wide, so insufficient evidence.
  • Toolset: lithography breakdowns that the twin does not model; it is wrong by hours.

Field 4: where the twin must not be used

  • Every condition outside the range the twin was calibrated and tested in: nothing supports a claim there.
  • Every tested condition whose verdict was misses or insufficient evidence.
  • Not a condition your tests included and that met the tolerance: the results support it, and listing it would hide what the twin can do.
Claim only what the data support. On simulated data, a result shows how the twin recovers the course's simulator, not how it would work on a real tool.

Field 5: one risk and its mitigation

A twin is only as good as the data it reads, and a twin that sends decisions back is a path into the tool (NIST IR 8356).

riska mitigation that reduces it
a measurement attributed to the wrong runmatch run ID and timestamp with the tool log; reject what does not match
an unauthorized change sent through the sync channeladvisory mode with authenticated, logged approval of every change
a predicted value recorded as if measuredlabel every value as predicted or measured

A mitigation that does not reduce the risk, such as widening the tolerance or retraining more often, is not a mitigation.

Field 6: when confidence is low

Stop relying on it

Hold the last approved setting, or switch to advisory mode.

Measure instead

Physical metrology, or the measured cycle times, until the cause is understood.

Bring it back on evidence

Use the twin again only when new data show it meets the tolerance.

Not: widen the tolerance, refit on the test data and call it validated, or switch to another method without recording it.

Validation is never finished

  • The furnace drifts, thermocouples are replaced, recipes and products change: the twin you validated last month describes a slightly different tool.
  • The National Academies' 2024 report on digital twins concludes that their verification, validation and uncertainty quantification must be a continual process.
  • A data sheet therefore carries a date, and the sync layer, the alarms of Module 5 and new held-out data keep testing the twin while it is used.

Summary

  • A twin is assembled from parts; the connection is code, and code needs verification.
  • Validation follows a plan written first: tolerance, held-out data, baseline, one challenging condition.
  • Score each prediction before its measurement is used, with one error per independent test unit.
  • The verdict compares the whole interval with the tolerance: meets, misses or insufficient evidence.
  • The data sheet records what the twin is for, how it did, where it must not be used, one risk and the low-confidence action.
